# 当前 Diff 审查流程

适用于用户要求 review、审查或检查工作区变更且本轮不修改代码的任务。

## 审查顺序

1. 读取项目说明、技术栈配置和 `git status --short`；确定变更基线和用户已有修改。
2. 查看完整 Diff，再追踪受影响入口、调用方、状态流、请求层、权限和公共组件。
3. 对照需求逐项检查行为、边界、复用、范围、公共契约、编码和兼容性。
4. 运行与变更最相关的解析、Lint、类型、测试或构建检查；检查 UI 时实际打开页面并验证关键状态。
5. 只报告可复现或有明确证据的问题，按阻断程度排序，给出文件、位置、影响、复现和建议。

## 报告格式

- **阻断问题**：会导致构建失败、核心流程不可用、数据/权限错误或明显回归。
- **重要问题**：需求缺失、边界错误、公共契约变化或可访问性/兼容性缺陷。
- **一般建议**：不阻塞交付但可改善可维护性或验证覆盖。
- **已验证项 / 未验证项**：列出实际命令、入口、视口和失败或缺失原因。

审查结论必须说明是否发现问题；没有证据时不要把风格偏好写成缺陷。
